1. Vue d'ensemble

L'application ASP.NET (port 7575) tourne dans un conteneur Docker. Elle n'est pas exposée directement : nginx-ui, qui gère HTTPS, la limitation de débit et le certificat, relaie les requêtes vers le conteneur sur un réseau Docker partagé.

2. Prérequis

  • Accès SSH au VPS avec sudo.
  • Docker Compose version 2.24 ou plus (le script utilise « ports: !reset [] »). Vérifier : docker compose version.
  • Le conteneur nginx-ui existe et publie les ports 80 et 443.
  • Le dépôt est cloné dans ~/ml-foot.
  • Un fichier appsettings.Production.json existe dans ~/ml-foot (voir la section 6) : il est monté dans le conteneur et n'est pas versionné.

3. DNS (BIND)

Chaque sous-domaine a un enregistrement A dans la zone BIND du VPS.

  1. Éditer le fichier de zone dans /var/lib/bind/ (nom du fichier : voir « zone » dans la configuration de BIND).
  2. Ajouter une ligne identique à celle de kraken, avec l'IP du VPS.
  3. Incrémenter le serial du SOA (format AAAAMMJJNN), sinon les serveurs secondaires ignorent le changement.
  4. Vérifier la zone, puis la recharger.
À savoir Si un fichier .jnl existe à côté de la zone, la zone accepte les mises à jour dynamiques : exécuter « sudo rndc freeze dbdesignandcodereview.com » avant l'édition et « sudo rndc thaw dbdesignandcodereview.com » après.
Attention Le journal « zone serial unchanged » signifie que le serial n'a pas été incrémenté.

4. Certificat Let's Encrypt

Un seul certificat (nom : dbdesignandcodereview.com, clé RSA) couvre tous les sous-domaines. Il est émis en mode standalone : certbot ouvre lui-même le port 80, que nginx-ui occupe. Il faut donc arrêter nginx-ui pendant la validation (environ 30 secondes d'indisponibilité de tous les sites).

Attention Les hooks enregistrés dans /etc/letsencrypt/renewal/*.conf ne s'appliquent qu'à « certbot renew ». Avec « certbot certonly », il faut redonner --pre-hook et --post-hook, sinon : « Could not bind TCP port 80 ».

Avant d'ajouter un sous-domaine, vérifier que tous les noms du certificat répondent encore sur ce VPS (un seul nom en échec fait échouer l'ensemble), puis sauvegarder.

Réponses aux questions de certbot :

  • « Update key type to ECDSA ? » : répondre K (Keep), pour conserver RSA.
  • « Did you intend to make this change ? » : répondre U (Update).
À savoir Le renouvellement automatique (certbot renew) arrête puis relance nginx-ui grâce aux hooks du fichier de renouvellement.

5. Déploiement de l'application

Attention Le nom du domaine se donne après --domain. Sans cette option, le script s'arrête (« --domain est obligatoire »). Toujours passer par le script : il fournit la version affichée dans le badge ; un « docker compose up --build » manuel affiche « dev ».

Ce que fait le script

  1. Application : détecte le réseau Docker de nginx-ui, génère docker-compose.override.yml (rattachement au réseau, port 7575 non publié), exporte la version (commit court + date), puis lance docker compose up -d --build.
  2. nginx-ui : installe prediction.conf avec le bon domaine et le bon certificat, sauvegarde l'ancienne version dans /var/backups/prediction-deploy/, exécute nginx -t, recharge nginx, puis interroge /api/health. Si nginx -t échoue, l'ancienne configuration est restaurée.
  3. fail2ban : installe le paquet s'il manque, copie les filtres et le jail, crée le fichier de journal, recharge fail2ban et affiche l'état des deux jails.

Résultat attendu

  • Le test de santé affiche « HTTP 302 » : c'est normal, l'API exige une connexion et redirige vers /Account/Login.
  • Les deux jails (prediction-auth et prediction-scan) apparaissent avec « Currently banned: 0 ».
  • L'avertissement nginx sur « listen ... http2 » dans livesales.conf concerne un autre site et est sans effet ici.

Ouvrir ensuite https://prediction.dbdesignandcodereview.com : la page de connexion doit s'afficher avec le cadenas valide. Le badge de version (en-tête et bas du menu latéral) doit afficher le hash du dernier commit.

6. Configuration de l'application et des clés

Les clés d'API se trouvent dans ~/ml-foot/appsettings.Production.json, monté en lecture seule dans le conteneur. Ce fichier n'est jamais versionné dans git.

  • Un simple redémarrage suffit : le fichier est monté, pas copié dans l'image.
  • Un JSON invalide fait échouer le démarrage : contrôler avec docker logs --tail 30 football-prediction.
  • Une clé qui a été affichée ou collée quelque part doit être régénérée chez le fournisseur et l'ancienne désactivée.
  • Les journaux HTTP des clients d'API sont au niveau Warning : les URL contenant la clé ne sont plus écrites.

Le fichier source est deploy/nginx-ui/prediction.conf ; le script l'installe dans /opt/nginx-ui/nginx/conf.d/prediction.conf.

JailDétecteSeuilDurée du ban

  • Les bans visent la chaîne DOCKER-USER : la chaîne INPUT par défaut ne protège pas les ports publiés par Docker.
  • ignoreip n'est volontairement pas défini (connexions depuis plusieurs lieux et un mobile, IP variables). Le jail ne couvre que les ports web : le SSH reste ouvert pour débloquer.
  • Le fichier de journal prediction-access.log doit exister avant le démarrage des jails : le script le crée.

9. Sécurité de l'application

  • En-têtes de proxy : l'application n'accepte X-Forwarded-For et X-Forwarded-Proto que depuis les plages privées (172.16.0.0/12, 10.0.0.0/8, 192.168.0.0/16). Pour restreindre au seul réseau de nginx-ui : variable ForwardedHeaders__KnownNetworks (par exemple 172.18.0.0/16) dans docker-compose.yml.
  • Cookie d'authentification : drapeau Secure en production (la connexion se fait donc par https://, pas par http://IP:7575).
  • Clés de chiffrement des cookies (DataProtection) : stockées dans data/keys, sur le volume ./data. Un redéploiement ne déconnecte plus les utilisateurs.
  • Le port 7575 n'est plus publié sur l'hôte : seul nginx-ui y accède, par le réseau Docker.
  • Les mots de passe suivent la politique Identity (8 caractères minimum, majuscule, minuscule, chiffre) ; verrouillage de 15 minutes après 5 échecs.

10. Mise à jour courante

  1. Vérifier que le conteneur est « Up » : docker ps --format '{{.Names}} {{.Status}}' | grep football.
  2. Vérifier le badge de version : il doit correspondre à git log -1 --oneline. « dev » indique un build hors du script ; un suffixe « -dirty » indique des modifications locales non commitées sur le VPS.
  3. Sur un téléphone, actualiser deux fois la première fois : le CSS est versionné par hash, mais l'ancienne page peut encore référencer l'ancien fichier.

12. Retour arrière

  1. Application : git log --oneline pour repérer le commit voulu, git checkout <commit>, puis relancer deploy.sh. Revenir ensuite sur main (git checkout main) avant le prochain git pull.
  2. Configuration nginx : copier /var/backups/prediction-deploy/prediction.conf.bak vers /opt/nginx-ui/nginx/conf.d/prediction.conf, puis nginx -t et nginx -s reload.
  3. Certificat : restaurer la sauvegarde /root/letsencrypt-backup-<date> (arrêter nginx-ui, remplacer /etc/letsencrypt, relancer nginx-ui).
  4. Docker : le fichier docker-compose.override.yml est regénéré à chaque déploiement ; l'ancien est conservé en docker-compose.override.yml.bak.<horodatage>.
